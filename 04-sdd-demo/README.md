# SDD 实践示例：投诉标签一致性校验服务

> 本示例用于说明 SDD 的**思想内核**：
> 当代码可以廉价生成时，昂贵的不是写代码，而是**对齐"什么是正确的"**。
> SDD 把"什么是正确的"从口头共识变成可版本化、可评审、可执行验证的产物。

---

## 一、SDD 是什么，解决什么问题

**问题起点**：AI 编码让实现成本急剧下降，但需求误解的成本没变——甚至更隐蔽了。
一段代码三分钟写完，但它实现的是**错误的需求**，而且看起来完全正常。

**SDD 的主张**：把研发流程的重心从"写代码"前移到"定义正确性"。

| 传统开发 | SDD |
| --- | --- |
| 口头/会议传递需求 | 规范（Spec）作为唯一真相源 |
| 编码时才知道要什么 | 先定义验收标准，再实现 |
| 测试是事后补充 | 验收标准即测试依据，测试是规范的执行 |
| 文档与代码分离且易腐烂 | 规范与代码同仓，CI 强制校验一致性 |

**与 TDD 的关系**：TDD 用测试定义正确性，SDD 用规范定义正确性。两者不冲突——
理想的 SDD 里，规范中包含可执行的验收测试，此时规范与测试合一。

**SDD 不是**：文档驱动的瀑布流。规范是活的、随产品演进而修订的（living spec），
不是一次写完就冻结的契约。

---

## 二、完整流程与产物

以 GitHub Spec Kit 的阶段划分（业界最通行的落地形态）：

```
constitution → specify → clarify → plan → tasks → analyze → implement
   项目宪法      需求规范    澄清补缺    技术方案   任务拆分    一致性检查    实现
```

### 阶段 0：constitution（项目宪法）

```markdown
# 项目原则

1. 所有分类逻辑必须引用 qc://schema/categories 中的口径定义，禁止代码内硬编码类别名。
2. 任何新增类别必须同步更新口径定义、评测集与文档三者，缺一不得合并。
3. 错误响应必须返回可读的业务错误文案，不得暴露堆栈。
4. 标签一致性校验的判定规则只允许来自已评审的规则集，不得由模型临时决定。
```

**为什么要这一步**：AI 编码时，约束不写下来就会被违反——模型不知道你团队的红线。
宪法是给 AI 看的"项目规则"，相当于人写代码时的团队规约。

### 阶段 1：specify（需求规范，只说 What 不说 How）

```markdown
# 功能：投诉标签一致性校验

## 用户故事
作为质检分析师，我希望对一批已标注工单做标签一致性校验，
以便识别标注规范中的模糊地带，为规范修订提供依据。

## 验收标准
1. 输入含 100 条标注记录（文本 + 人工标签），输出每条的校验结论。
2. 结论分为三类：一致 / 口径歧义 / 明确错误，并给出每条的依据条款。
3. 输出中"口径歧义"条目必须引用具体的口径定义条款编号，不允许只写"存在歧义"。
4. 汇总结果给出三类各自的占比，且三类占比之和为 100%。
5. 当输入记录数少于 30 条时，程序必须拒绝执行并说明原因，不得降级为部分输出。

## 非目标（明确不做）
- 不做标注质量的自动修正（只做校验，不做修改）
- 不做模型训练
- 不支持除上述四类以外的类别体系

## 约束
- 单次处理 100 条的耗时 ≤ 5 秒（不含模型推理）
- 必须输出机器可读的 JSON，同时提供人类可读摘要
```

**这段规范里最值钱的两条**：
- 验收标准第 3 条：把"必须引用条款"写死——这是**可验证**的，不是"要专业一点"这种废话；
- 验收标准第 5 条：**明确拒绝的边界**。很多需求失败不是因为没做该做的，而是因为做了不该做的。

### 阶段 2：clarify（澄清）

规范写完后要主动找歧义。本例会被追问的问题：

- "口径歧义"的判定标准由谁定？答：由已评审的规则集决定（阶段 0 原则 4）。
- 校验结论由 LLM 判定吗？答：规则集优先；LLM 仅在规则无法覆盖时给出候选，标记为"待人工复核"。
- 输入格式是什么？答：JSONL，每行 `{"id","text","label"}`。
- 拒绝执行时返回什么？答：HTTP 400 + 结构化错误体，`error_code: INSUFFICIENT_SAMPLES`。

**这一步的工程意义**：把歧义消灭在编码之前，成本是 10 分钟对话，收益是避免一轮返工。

### 阶段 3：plan（技术方案，说 How）

```markdown
# 技术方案

## 架构
输入校验层 → 规则匹配层 → (LLM 兜底层) → 结论生成层 → 汇总层

## 关键决策
1. **口径定义单一来源**：从 Resource `qc://schema/categories` 读取，不硬编码。
2. **规则优先、LLM 兜底**：规则命中即出结论；未命中才调 LLM，且 LLM 结论标记待复核。
3. **结构化输出**：用 JSON Schema 约束 LLM 输出（strict 模式），不用"请输出 JSON"的提示词。
4. **逐条可追溯**：每条结论携带 `rule_id` / `policy_ref`，支持抽查。

## 风险与对策
| 风险 | 对策 |
| --- | --- |
| LLM 输出结构不稳定 | JSON Schema strict 约束 + 解析失败重试 1 次后降级为"待复核" |
| 口径定义变更导致规则失效 | 规则集带版本号，加载时与口径版本比对，不一致则拒绝启动 |
| 样本量不足导致占比失真 | 硬性门槛 < 30 条拒绝执行（见验收标准 5） |
```

**注意决策 2**：这就是手册里"模型分级路由"的实际落地——
能用规则解决的绝不调 LLM，LLM 只在规则覆盖不到时兜底，且兜底结果不自动采信。

### 阶段 4：tasks（任务拆分）

```markdown
- [ ] T1 定义输入数据模型（pydantic，含样本量下限校验）
- [ ] T2 实现口径定义加载器（读 Resource，校验版本）
- [ ] T3 实现规则匹配层（每条规则含 rule_id 与 policy_ref）
- [ ] T4 实现 LLM 兜底层（JSON Schema strict + 解析失败降级）
- [ ] T5 实现结论生成与汇总（三类占比计算，断言和为 100%）
- [ ] T6 实现 CLI 入口（JSONL 输入，JSON + 摘要输出）
- [ ] T7 编写验收测试（对应验收标准 1-5 逐条覆盖）
```

**拆分标准**：每个任务足够小、可独立验证、能被一个 PR 覆盖。
`"创建校验接口并确保返回结果"` 是任务；`"创建返回校验结果的校验接口"` 不是。

### 阶段 5：analyze（一致性检查）

实现前检查规范、方案、任务三者是否矛盾。本例会发现的典型冲突：

- 规范第 4 条要求"三类占比之和为 100%"，但方案里"明确错误"和"口径歧义"存在重叠可能
  → **修正**：明确优先级判定顺序（口径歧义 > 明确错误），并在规则集中写死
- 规范验收标准 5 与方案的风险表一致，无需改动

**这一步能省一次 code review 阶段的返工**——矛盾在编码前暴露，而不是在合并时。

### 阶段 6：implement（按任务实现 + 评审）

实现阶段的关键纪律：**每次只实现一个任务，产出小而可评审的变更**，
而不是让 AI 一次生成整个项目（那样产出的 diff 无法有效评审）。

## 三、SDD 的边界与失败模式

| 失败模式 | 表现 | 应对 |
| --- | --- | --- |
| **验证缺口** | AI 声称满足规范，实际没做到 | 只有可执行测试能让"符合规范"成为机械事实，不能靠声称 |
| **规范腐烂** | Spec 与代码逐渐不一致，误导后续 AI | 规范与代码同仓；CI 校验规范与实现一致性 |
| **过度规定** | 规范写成实现说明书，限制方案空间 | 规范说"是什么"，方案说"怎么做"，别越界 |
| **规定不足** | 规范太松，AI 自行脑补并幻觉 | 关键决策必须显式写出，包括"不做什么" |
| **规范忠实但设计错误** | 规范准确编码了一个坏设计 | SDD 提升的是保真度，不是判断力——设计评审仍不可省 |
| **复杂度反噬** | 小改动也要写全套文档 | 只在高风险、意图有争议的工作上用，CRUD 不需要 |

## 四、SDD 在我实际工作中的应用方式

不打算为了用 SDD 而用 SDD。我的实践是**按风险分级**：

| 变更类型 | 是否走完整 SDD | 理由 |
| --- | --- | --- |
| 改个文案、调个样式 | 否 | 意图无争议，规范的成本高于收益 |
| 新增一个业务规则 | 部分（规范 + 验收标准） | 口径需要明确，否则会被误实现 |
| 新增一个对外接口 | 是 | 对外契约错误影响面大，必须先定验收 |
| 重构核心数据链路 | 是 | 影响面广，必须有完整规范与回滚预案 |

**最实用的一条**：哪怕不引入任何工具，
**在让 AI 写代码之前，先把"完成的标准是什么"写成一个列表**——
哪怕只有 5 条。这一步就能消除大部分返工。这就是 SDD 的最小内核。

## 五、工具链

| 工具 | 形态 | 说明 |
| --- | --- | --- |
| **GitHub Spec Kit** | 开源 CLI | 最通行的 spec-first 流程，支持 20+ 编程 Agent，`/speckit.specify`→`/speckit.plan`→`/speckit.tasks`→`/speckit.implement` |
| **Amazon Kiro** | IDE | 生成 `requirements.md` / `design.md` / `tasks.md` 三件套 |
| **AGENTS.md / CLAUDE.md** | 仓库级约定 | 给 Agent 的持久化项目规则，相当于 constitution 的轻量版 |
| **OpenAPI / JSON Schema / Pact** | 契约 | 机器可校验的接口契约，让"符合规范"可被 CI 检查 |
| **TLA+ / Alloy** | 形式化 | 用于确实不能错的逻辑（如支付状态机、权限模型） |

**注意**：这一类工具 2026 年仍在快速演进，没有事实标准。
讲清楚**思想**比背工具名重要得多。
