# 项目 05：自进化质检 Agent（经验回流闭环）

> 本作品实现一个受评测门禁约束的经验回流闭环：人工纠正 → Skill 补丁提案 → 门禁评测 → 版本化发布。

---

## 这个作品解决什么问题

前四个作品解决的是"Agent 能干活"。第 5 个解决的是"Agent 干得越来越好"。

真实业务里有一个反复出现的困境：模型上线后，业务方持续发现新的错误模式；团队每次靠人工排查、手工改提示词或补样本，改完就结束——**经验没有沉淀，下一个人/下一轮还要重来一遍。**

这个作品实现一条完整闭环：

```
人工纠正 → 提炼为 Skill 草案 → 评测集验证 → 通过则纳入版本管理 / 不通过则回退
↑↓
下一轮任务自动加载
```

---

## 实现说明

本作品用 Python 标准库独立实现，不依赖第三方运行时：

- 场景：电信投诉工单 bad case 归因
- 评测集：自建四类错因体系（见下）
- 门禁逻辑：自实现的四项检查与回归预算判定

---

## 为什么这个场景值得做

场景选**电信投诉 bad case 归因**，因为它让闭环可度量：

1. **评测集有明确标签**：四类错因（口径混淆 / 边界误判 / 归因浅层 / 结论越界）各有唯一期望结果
2. **Skill 有业务语义**：从纠正中提炼出的是"这类错该怎么改"，不是行文风格偏好
3. **闭环可验证**：Skill 修订前后，可以用留出的 bad case 集量化对比

---

## 四类错因体系（评测集的基础）

| 错因类型 | 识别特征 | 对应 Skill 应做什么 |
|---|---|---|
| 口径混淆 | 同一术语按不同定义理解 | 补充口径定义到 Resource，不改分类逻辑 |
| 边界误判 | 分类时把边缘 case 划入邻近类别 | 补 few-shot 样本，显式标注边界 |
| 归因浅层 | 只描述现象不追根因 | 强制归因链路，拆到流程环节 |
| 结论越界 | 把待验证假设陈述为确定结论 | 增加统计显著性检查与反向指标 |

**关键设计**：这四类的修复动作**完全不同**——有的改规范、有的改样本、有的改流程。如果 Agent 每次都用同一种方式"修复"，那它没有真正学到归因。

## 架构

```
① 纠正采集层
   data/corrections.jsonl  ← 人工纠正记录（根因 + 正确动作）
            │ 提取
            ▼
② Skill 提案层
   从纠正记录归纳"这类错该怎么改" → Skill 草案（增量 patch）
   产出：skill_candidate.json
            │ 提交评测
            ▼
③ 评测门禁层（admission gate）
   · 留出集（held-out）上跑：Skill 版本 vs 基线版本
   · 回归预算：历史任务准确率下降超过阈值 → 直接拒绝
   · 目标子集必须提升（不只看整体）
   产出：evaluation_report.json（PASS / REJECT + 依据）
            │ PASS
            ▼
④ 版本管理层
   config/skills/ 下版本化存储，附变更说明与评测报告
   下一轮任务自动加载最新版
```

## 四个设计决策

### 决策 1：为什么 Skill 必须"过门禁"才能上线

Agent 生成的 Skill 草案**天然是不可信的**——它可能是对的，也可能是模型幻觉出的错误经验。

如果直接采纳，一次错误修订就会污染后续所有任务，且**错误会被固化进 Skill，越滚越大**。

所以我实现了硬门禁，四项检查全过才 `PASS`：
- 必须**在留出集上优于基线**
- 必须**不超出回归预算**（历史任务准确率下降 ≤ 阈值）
- 必须**在目标错因子集上有提升**（防止"整体涨了但目标没变"的假进步）
- 目标子集**样本量须达下限**（样本太少时统计噪声大于真实收益）

### 决策 2：为什么"整体准确率提升"不算数

这是我在 `03-skill/SKILL.md` 里已经写过的一条 Pitfalls：

> 整体准确率从 88% 到 89% 可能毫无意义，必须看目标子集。

假设有 1000 条样本，目标错因占 80 条。修好 40 条让整体提升约 4pp；但如果**同时弄坏了别的 35 条**，净提升只剩 0.5pp，几乎被统计噪声淹没。整体指标完全掩盖了这个问题。

所以门禁判定的第一个条件是**目标子集提升**，整体指标只是参考。

### 决策 3：为什么回归预算要独立于提升指标

有个陷阱：新 Skill 让目标子集涨了 10%，但让其他子集掉了 15%，整体还是跌的。

**门禁必须同时看两个方向**：
- 目标子集：必须涨（收益）
- 历史任务集：跌幅不能超过预算（代价）

这就是**回归预算（regression budget）**原则——**允许进化，但不允许悄悄退化。**

### 决策 4：为什么 Skill 补丁是"增量"而非"重写"

增量修订是这里的关键取舍。原因在机制上：

生成的完整重写会替换整份文档，输出里没重复出现的规则就永久丢失，包括历次迭代积累的查询与归档方法；而且这种丢失是静默的，结果看起来仍然完整。

所以本实现的 Skill 提案是**增量 patch**，只改需要改的段落，保留其余原文。`03-skill/SKILL.md` 里的 "Pitfalls" 段就是重点保护对象——**积累的反例最难重建，不能被自动修订悄悄抹掉。**

## 运行

```bash
python evolve.py                     # 跑一次完整闭环（采集→提案→门禁→发布）
python evolve.py --dry-run           # 只提案，不发布（模拟评审中）
python evolve.py --eval-only         # 跳过提案，直接对当前 Skill 跑门禁
```

**输出示例**：

```
[1/4] 采集纠正：18 条记录，涉及 4 类错因
[2/4] 生成提案：4 个增量 patch
[3/4] 评测门禁
        基线 v1：目标 0.0% / 留出 0.0% / 历史 50.0%
        候选 v2：目标 68.2% / 留出 65.4% / 历史 32.5%
        判定：REJECT｜历史任务集回撤超预算：17.50pp > 3.0pp
[4/4] 受控发布：门禁未通过，Skill 保持 v1 不变
```
