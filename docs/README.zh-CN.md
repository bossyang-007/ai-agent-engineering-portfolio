## 这个仓库在讲什么

大多数 Agent 演示止步于「Agent 能干活」。这个仓库关注的是更难的问题：
**怎么让 Agent 从反馈里持续改进，同时不让它悄悄退化？**

四类反复出现的失败模式构成了设计动机：口径定义不一致、边界误判、归因浅层、结论越界。
它们在整体指标上都可能表现为「提升」，却同时在某个子集上造成退化——这正是第 5 个项目
把评测门禁、回归预算与目标子集评分放在每次自我修改之前的原因。

## 项目 05：把前四个串成闭环

```
人工纠正 → Skill 补丁提案 → 评测门禁 → 版本化发布
↑                                              │
└────────────── 下一轮任务自动加载胜出版本 ─────┘
```

门禁有**四项独立检查**（目标子集样本量门槛、目标子集提升、回归预算、留出集泛化），任何一条不过就拒绝：

```
[1/4] 采集纠正：18 条记录，涉及 4 类错因
[2/4] 生成提案：4 个增量 patch
[3/4] 评测门禁
      基线 v1：目标 0.0% / 留出 0.0% / 历史 50.0%
      候选 v2：目标 68.2% / 留出 65.4% / 历史 32.5%
      判定：REJECT｜历史任务集回撤超预算：17.50pp > 3.0pp
[4/4] 受控发布：Skill 保持 v1 不变，完整证据留痕
```

### 四个值得展开讲的设计决策

**1. Agent 生成的 Skill 草案天然不可信**
它可能是对的，也可能是幻觉出来的错误规则。直接采纳，一次坏修订就会污染后续所有任务，
而且错误会被固化进 Skill 越滚越大。所以每个 patch 都必须在**留出集**上跑赢基线。

**2. 整体准确率提升不算数**
1000 条样本里目标错因只占 80 条，修好 40 条整体就涨 4 个点；
**但如果同时弄坏了别的 35 条，净变化几乎为零。**
所以门禁永远先看**目标子集**，整体指标只作参考。

**3. 回归预算独立于提升指标**
新版让目标子集涨 10%、其他子集跌 15%，整体还是跌的。两个方向必须同时检查。
这就是**回归预算（regression budget）**原则：**允许进化，不允许悄悄退化。**

**4. 只做增量 patch，绝不整条重写**
生成的重写版会替换整份文档，输出里没重复出现的规则就永久丢失，包括历次迭代积累的条目；
而且这种丢失是静默的，结果看起来仍然完整。所以提案只允许在四个指定锚点段落追加，
Pitfalls 段对提案方只读：积累的反例是最难重建的内容。

实测：Skill 从 **108 行变成 112 行**，四个锚点各加一行，原有段落逐字未动。
这条断言已写进 CI 流水线，每次推送自动校验。

### 亲自验证门禁（可运行证据）

上面四项检查不只是文字描述，而是**可执行的证据**。`verify_gate.py` 用与 `evolve.py`
完全相同的 `gate.py` 函数，从仓库内已提交的 `data/eval_set.json`（88 条样本）重新计算
基线版与候选版的分数，然后断言：

- 默认 3.0pp 回归预算会以**恰好一条**理由**拒绝**候选版；
- 把预算放宽到 20pp 后，**同一个**候选版会**通过**；
- 四项检查中的任意一项都能被**单独**触发失败，且每一条失败都会拒绝这次改动。

它只依赖标准库、纯离线、只读——不会改动受版本管理的 Skill，也不会写 `logs/`，
因此运行它不会弄脏工作区。运行后可直接看到每个场景的判定：

```bash
python 05-self-evolving-qc-agent/verify_gate.py
# OK: 27/27 assertions passed.
```

任何一条断言不成立，脚本即以非零码退出；CI 每次推送也会运行它——
「允许进化，不允许悄悄退化」这句话因此不会随代码演进而悄悄失效。

## 为什么用投诉归因场景

场景是**投诉 bad case 归因**：给定一个错分案例，判断它属于四类错因中的哪一类、该做什么修复。
选它是因为这个场景让闭环可度量：

1. **评测集有明确可校验的失败模式**——四类错因（口径混淆 / 边界误判 / 归因浅层 / 结论越界）
   每一类都有唯一确定的期望标签。
2. **提炼出的规则有业务含义**——学到的是「这类错该怎么改」，不是行文风格偏好。
3. **闭环可量化**——用留出的 bad case 批次就能量化一次修订到底有没有用。

关键在于：四类错因需要**完全不同的修复动作**——有的改规范、有的补样本、有的改流程。
如果每次都用同一种方式「修复」，那它根本没学到归因。

## 范围与局限

本项目已实现并验证：
- 完整闭环：纠正采集 → 补丁提案 → 门禁评测 → 受控发布，四个阶段相互独立
- 回归预算与目标子集评分两者缺一不可的原因
- 采用增量修订的原因，以及整条重写丢弃既有规则的具体机制
- 三段式评测集的构造方式，以及四类错因体系的来源

局限：
- 设计采用受控变更与回归预算的通用工程原则，本仓库不提出新范式。
- 这是精简的纯离线参考实现，未在真实生产流量或在线模型 API 下运行。
- 评测集为自建合成数据，共 88 条样本，评分过程为确定性模拟。结果说明的是「门禁会拦住引入回归的改动」，不构成模型准确率提升的一般性结论。
