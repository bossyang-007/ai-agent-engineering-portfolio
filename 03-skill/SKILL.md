# 投诉 Bad Case 归因分析

## 这个 Skill 解决什么问题

模型把投诉错分了，下一步该做什么？——**先归因，再对症下药**。
不同根因的解法完全不同：口径混淆要改规范，边界误判要补样本，特征不足要加规则，标签噪声要清洗数据。
**跳过归因直接优化提示词或换模型，是这类项目最常见的浪费。**

本 Skill 把归因流程标准化：输入一批错判样本，输出根因分布 + 改进建议清单。

## 何时使用

- 拿到模型误判样本，要判断"是哪里错了"
- 分类准确率上不去，要定位瓶颈在规范、数据还是模型
- 要给 few-shot 挑示例，需要知道模型在哪类模式上系统性失手
- 要修订标注规范，需要把"人也会分歧的边界"显式写出来

**不要用于**：单条样本的分类判断（直接用 `classify_complaint` 工具）；完整口径库查询（读 Resource `qc://schema/categories`）。

## 执行步骤

### 第 1 步：确认输入完整性（必做，不要跳过）

开始前必须确认：
- 样本总数 ≥ 10 条。少于 10 条的统计没有意义，此时应说明"样本量不足，结论仅供参考"
- 每条样本包含：原始文本 + 人工标注标签 + 模型预测标签
- 明确本次分析的时间范围与数据来源

缺任何一项，**先向用户说明缺什么**，不要自行假设。

### 第 2 步：逐条打根因标签

对每条错判样本，归入以下四类之一（互斥，按优先级判定）：

| 根因 | 判定标准 | 典型特征 |
| --- | --- | --- |
| **口径混淆** | 人工和模型依据的是不同的类别定义 | 人工按"业务影响"归类，模型按"字面关键词"归类 |
| **边界误判** | 两者依据同一口径，但样本落在边界上 | 文本同时含两类特征，或属于定义未覆盖的灰区 |
| **特征不足** | 口径明确，模型因缺关键信息而错判 | 需要上下文（时间、套餐、地区）才能判断 |
| **标签噪声** | 人工标注本身有误 | 与类别定义明显冲突，或标注者未读定义 |

判定优先级：口径混淆 > 边界误判 > 标签噪声 > 特征不足。
理由：口径问题会连带污染样本，若先修样本是在错误地基上盖楼。

### 第 3 步：量化分布

- 统计四类根因各自占比，按占比降序
- 标注"主要矛盾"：占比最高的那一类
- **不要平均用力**——明确指出资源应优先投向哪一类

### 第 4 步：给出改进建议（对应到具体动作）

每条根因对应具体动作，不接受"优化模型"这种空建议：

- 口径混淆 → 修订类别定义，在定义中补充易混淆类别的**区分判据**（正例 + 反例）
- 边界误判 → 补充该边界的标注样本，并在定义中显式写出"优先归入X"的选择规则
- 特征不足 → 补充所需上下文字段，或把该判定前移为规则
- 标签噪声 → 清洗该批样本，必要时重新标注并复核标注者一致性

### 第 5 步：给出验证方式

每条建议必须附**可验证的方式**，否则无法判断是否真的改进：

- 明确评测口径：用什么指标衡量（如边界样本的准确率、而非整体准确率）
- 给出评测集规模建议与抽样方式
- 说明预期变化方向（不要承诺具体数值）

## 常见陷阱（Pitfalls）

- **不要用整体准确率论证局部改进**：整体准确率从 88% 到 89% 可能毫无意义，必须看目标子集
- **不要跳过第 1 步**：小样本上的根因分布是噪声，照着改会引入错误规则
- **不要混淆"模型错了"和"口径没定义"**：这两者的解法完全不同，前者改模型，后者改规范
- **不要给没有证据的因果判断**：说"数据分布偏斜导致"，必须能指出分布证据
- **区分观察与推测**：输出中"观察到 X"和"推测原因是 Y"必须分开表述

## 验证清单（交付前自查）

- [ ] 每条样本都打了根因标签，无遗漏
- [ ] 根因占比之和为 100%
- [ ] 指明了主要矛盾，只有一个
- [ ] 每条建议都对应到具体动作，没有"优化模型"式空建议
- [ ] 每条建议都有可验证方式
- [ ] 观察与推测分开表述

## 交付格式

```
## 归因结论
样本量：N 条（时间范围：XXX）
主要矛盾：<根因类别>，占比 X%

## 根因分布
| 根因 | 条数 | 占比 | 典型案例 |

## 改进建议（按优先级）
### 1. <根因> → <具体动作>
   - 验证方式：<指标 + 评测集规模>
   - 预期方向：<方向，不承诺数值>

## 遗留问题
<未能从样本判定、需要补充信息才能回答的部分>
```
